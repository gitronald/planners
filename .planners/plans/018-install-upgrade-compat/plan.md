# Keep install working across planners upgrades

## Plan

### Problem

Two things make `planners install` harder to script than it should be when a
host moves from an older release to the current one.

1. **The scope flag was not stable.** Earlier releases accepted
   `install --global`. The 0.6.x line dropped it (only `--local` remained,
   with global the default), and the pkgskills mount (`9369792`) brought
   `--local/--global` back. A script that passed `--global` failed with
   `No such option: --global` on 0.6.x. No test pins the flag pair, so the
   same churn can recur unnoticed: `tests/test_host.py` exercises
   `install --local`, and `--global` appears only in the `permissions`
   tests.
2. **An upgrade refuses the files the previous release wrote.** A host that
   last ran `planners install` on a pre-adoption release (stamp
   `<!-- generated by planners X.Y.Z (mode=global); do not edit — run:
   planners install --force -->`) and then upgrades gets `foreign` for both
   the holder and the rule, and `install` without `--force` exits 1. That is
   deliberate and tested (`test_a_pre_adoption_holder_is_foreign_until_forced`):
   pkgskills cannot tell an untouched old render from a hand-edited one,
   because both carry this dist's name in a stamp pkgskills did not write.
   The cost is that every upgraded host needs `--force` once, and a
   provisioning script that wants to be safe on a fresh host has to pass
   `--force` always, which also overwrites genuinely hand-edited files.

### Approach

1. **Pin the scope flags.** Add tests that `install --global` and
   `install --local` are both accepted (with `--check` and with a write),
   and that no flag means global.
2. **Recognize this package's own pre-adoption stamp as stale, not
   foreign.** The pre-adoption stamp format is fixed and known: a single
   `<!-- generated by planners <version> (mode=<mode>); do not edit — run:
   ... -->` line. When the holder or rule carries exactly that line, and its
   `mode` matches the install being run, classify the file `stale`, so a
   plain `install` rewrites it and `--check` reports `stale` with
   `planners install` as the remedy. Anything else keeps today's `foreign`
   path: a different dist's stamp, no stamp, a mangled pkgskills stamp, or a
   pre-adoption stamp whose mode differs.
   - Mechanism to decide in implementation: a host hook in pkgskills (a
     legacy stamp pattern the host declares and `classify` consults), or a
     planners-side pre-pass before the pkgskills install runs. Prefer the
     pkgskills hook if pkgskills accepts it, since any other package that
     adopted pkgskills after shipping its own stamps has the same gap.
   - Update `test_a_pre_adoption_holder_is_foreign_until_forced`: a matching
     pre-adoption stamp upgrades without `--force`; an edited body under the
     old stamp is still overwritten (the stamp said "do not edit"), which is
     the tradeoff to accept and document; a mode mismatch stays foreign.
3. **Docs.** Add an upgrade note to the README: a pre-adoption install
   upgrades with a plain `planners install`.

### Revised for pkgskills 0.6.0

pkgskills 0.6.0 shipped the hook (`Host.legacy_stamps`), so the mechanism question in
Approach 2 is closed. Where this section and the Approach differ, this section holds.

1. **Status.** An old stamp reads `drifted`, not `stale`. In pkgskills `stale` means a
   superseded copy to remove, and rewriting one would recreate it.
2. **Mode mismatch.** An old stamp in the other mode reads `drifted` and a plain install
   rewrites it. It does not stay `foreign`.
3. **Remedy text.** `--check` prints `repair: planners install --force` for a `drifted`
   file, and a plain `planners install` also fixes it. The README says so.
4. **Removal.** A file with a declared stamp counts as generated everywhere, so a global
   install also removes a local copy of it, and an old `plan-files.md` rule. In a repo
   that tracks `.claude/`, that shows as a deletion in `git status`. This is what a
   current stamp already does. Document it next to the overwrite tradeoff.
5. **Upgrades beyond the old stamp.** Moving to 0.6.0 changes every host once:
   - Files with the `via pkgskills` comment read `drifted`, and a plain install
     refreshes them.
   - The rule gains a frontmatter block.
   - The Codex harness is on by default, so `.agents/skills/planners/SKILL.md` reads
     `missing` until a plain install writes it. `install --check` exits 1 until then.
6. **Docs grow.** The README says the skills are Claude Code only, and its install step
   lists only the `.claude` paths, so both need updating. pkgskills asks a host to say
   in the changelog of its first release on 0.6.0 that no `--force` is needed.

### Out of scope

- Recognizing older renders by content (hashing past releases' output).
- Changing how pkgskills treats other dists' stamps.
