# Plan Files

Plan-file lifecycle is owned by the **`planners`** package (installed; the
`/planners` skill). Create, activate, log, close, index, and backfill plans through
`/planners` — not by hand. The package is the **source of truth**: run `{cli} schema
PlanMetadata` for the canonical field list and `{cli} validate` to check conformance
(a pre-commit hook gates it once registered — registration is per-clone and
best-effort, so never assume it fired). This file is the always-on summary, itself
generated by `{cli} install` — do not hand-edit it; edit the convention in the package
and reinstall.

## Outside a repository

`{cli}` refuses to run outside a git repository: the command exits 1 and changes nothing.
That is not a broken install, and `{cli} install --force` is refused the same way, so there
is nothing to repair. Work from a repository, or run `git init` first. `skill`, `doc`,
`rule`, `schema`, `validate`, `permissions`, and `--help` run anywhere, and `index`, `base`,
and `remote` check the path they are given.

## Storage layout

Plans live under **`.planners/`** at the repo root (git-tracked despite the leading dot):

    .planners/
      README.md                     # generated "# Plans" index table — do not hand-edit
      plans/<NNN>-<slug>/plan.md    # one DIRECTORY per plan (sidecar files allowed)
      plans/<NNN>-<slug>/subplans/<letter>-<step>.md    # nested subplans, once a plan is split

Identity (`id`/`slug`) validates against the **directory name**. Regenerate the index with
`{cli} index .` after changes; never hand-edit `.planners/README.md`. Human-authored docs
live in `docs/` — a curated `docs/README.md` landing page, never a generated plan table.

`{cli} validate` fails when the tracked index disagrees with the plan frontmatter, so an
edit that changes a plan's title, status, `concluded`, or `pr` must be committed together
with a refreshed index. The lifecycle commands refresh and commit it themselves, and `log`
repairs a stale one it finds; after a hand edit to frontmatter, or a merge you resolved by
hand, run `{cli} index .` before committing (`validate --no-index` skips the comparison).
`install` marks the index `merge=union` and wires a `post-merge` hook that regenerates it,
as an **uncommitted change**, after a clean local merge; the `index` skill covers the merge
cases, including the conflicted merge and the PR that GitHub still reports as conflicting.

> **Migration in progress.** Some repos are still on the legacy `docs/plans/{NNN}-{slug}.md`
> + `TODO.md` layout. Keep using that layout in a repo until it is migrated to `.planners/`;
> new plans and migrated repos use `.planners/`.

## Naming

`<NNN>-<slug>` directory with an auto-incrementing prefix; **the first plan in a fresh
repo is `000`**, and a number is never reused. `{cli} add <slug>` assigns the number and
scaffolds the directory, `plan.md`, and conformant frontmatter.

For **batch creation**, do not run parallel `{cli} add`s — they can race on the
number. Instead, each creator runs `{cli} add <slug> --defer` to stage an
unnumbered plan under `.planners/staging/` (no commit, no shared state), then a
single `{cli} finalize` orders them by `created`, assigns sequential numbers,
materializes them under `plans/`, commits the batch, and self-checks — the sole
writer, so there is no race.

## Frontmatter

Every `plan.md` starts with YAML frontmatter of exactly seven keys, in this order:
`id, slug, status, branch, created, concluded, pr` (`id` is the NNN prefix as an integer,
`slug` the directory slug, `created` an ISO timestamp with its UTC offset). A **lettered
subplan** adds `sub:` (its letter) directly after `slug`; every other plan omits the line
rather than writing it empty. `{cli} add` writes the frontmatter, and
`{cli} schema PlanMetadata` is the authority on it.

> **Field name.** The terminal-timestamp field is **`concluded`** — renamed from `completed`,
> shipped in planners 004 (>= 0.2.0) as a hard cutover with **no read-alias**. A legacy plan
> still keyed `completed:` fails `validate` (its `concluded` parses empty) until the key is
> renamed; rename the first frontmatter occurrence per file when migrating.

`status` is one of `draft`, `active`, `implemented`, `blocked`, `done`, `inactive`, `retired`
(the shipped enum; the neutral terminal status is `retired`, with no failure connotation). Update
it as work progresses: `draft` -> `active` -> `implemented` -> `done` (or `retired`).
Use `implemented` once the implementation is **finished and its PR is ready for review**:
everything committed and pushed, waiting on a person to accept the work. `{cli} implemented
{NNN}` sets it from `active`, appends a Log entry, commits on the feature branch, and takes the
PR out of draft (`gh pr ready`); it refuses while the branch has uncommitted or unpushed work, and on the mainline.
It is an open state, so `concluded` stays empty and an umbrella does not close over a subplan
in it. It closes nothing: merging, the Retrospective, and `concluded` stay with `close`. Review
feedback that needs more work returns it to `active` with `{cli} activate {NNN}`, run on the
feature branch.
Use `blocked` for work that is **waiting on a person**: a decision, a manual check, access only
they have. `{cli} block {NNN}`, run on the mainline, sets it. It differs from `implemented`, which
waits on a person to accept finished work;
`blocked` waits for something the work itself needs. It is an open state like `active`, so `concluded` stays empty and nothing closes over
it. It is distinct from `draft` (not started) and `inactive` (set aside). Say what it waits on:
in the plan's Handoff section, or for a nested subplan in the Note column of the umbrella's table.
Use `inactive` for a plan that is parked or set aside without being implemented — considered
and deliberately shelved (e.g., it resolved to a one-line caveat, or describes a feature since
removed upstream) — but not formally closed and **may be revisited**. An `inactive` plan keeps
`concluded`, `branch`, and `pr` empty (it was never concluded); because `concluded` is empty it
sorts after done plans in the generated index.
Use `retired` for a plan that is **terminally closed because it was superseded or is no longer
needed** — e.g. its deliverable was absorbed into another plan or shipped by a different
mechanism. Unlike `inactive` it will not resume; it carries no failure connotation (the goal
was met another way, or made moot) — the neutral "this is dead" state. Fill `concluded` with
the date it was retired, and treat absent `branch`/`pr` as explicit `null` (it's
closed), the same as `done`.
Never type a timestamp. The CLI writes them: `{cli} log` stamps a Log entry from the
clock as it writes it, and `{cli} conclude` (for `done`) and `{cli} retire` (for `retired`)
fill `concluded` from git — `conclude` from the authored date of the branch's last work
commit, not the plan's own paperwork after it. None takes an option that sets the time.
`validate` fails a `concluded` earlier than `created`, so both commands write `created`
instead when the date from git is older than the plan (work committed before the plan was
written).
Leave `concluded` empty for `inactive` plans (they were parked, not concluded). Where no
command covers a stamp, read it from the clock (`date -Iseconds`) or from git
(`git log --format="%aI"`), never from memory.
Fill `pr` with the full PR URL (e.g., `https://github.com/owner/repo/pull/1`), not just the
number. `{cli} set-pr {NNN} <url>` writes it, refreshes the index, and commits.

**Generated Log entries.** `{cli} activate` appends an `Activated.` entry (branch, base
branch and commit, worktree, PR) to the plan's `## Log`, creating the section ahead of
Handoff and Retrospective when it is missing, so every plan records where its work lives.
`--worktree <path>` (repo-relative) records a worktree other than
`.worktrees/<NNN>-<slug>`, and `--no-worktree` records the main checkout. `set-pr` adds `PR opened: <url>`, `implemented` adds
`Implemented: <n> commits ahead of <base>`, and a return from `implemented` writes
`Reactivated`, so the Log reads as a timeline.

**Empty vs `null`.** An empty value (`pr:`) means "pending / not yet determined" — use it for
a field that may still be filled (an open plan's `concluded`/`pr`, or a branch not yet
assigned). Explicit `null` means "closed and confirmed absent" — use it only once a plan is
**closed** (done/retired, not `inactive`) and a field is genuinely N/A, e.g. it merged with no
dedicated PR (`pr: null`) or involved no branch (`branch: null`). An `inactive` plan uses empty
(pending) fields, not `null`, since it may resume. Both parse to YAML null, but the distinction
is a readable signal. Never write the string `none`/`None` — YAML reads those as strings.

## Title

Every plan needs a `# Title` heading after the frontmatter. Do not include the plan number or
"Plan:" prefix — the number is in the directory name. The title must describe the work, not be
generic (not "Plan", "Update", "Fix"). Write it in **sentence case**, not Title Case —
capitalize only the first word and any proper nouns or code identifiers (e.g.
"Migrate pandas to polars", "Add compressed test fixtures for CI", "Honor core.hooksPath when
detecting the hook"), never "Migrate Pandas To Polars". A good title summarizes the goal or
change.

## Body Sections

- **Plan** — implementation spec (required)
- **Log** — chronological notes, commits, decisions (optional, append during work)
- **Handoff** — the present state, for whoever picks the plan up next (optional, between Log
  and Retrospective, rewritten in place)
- **Retrospective** — post-completion insights (optional, add when done)

### Handoff

Held questions and "where to pick this up" need a home in the plan, or they end up in chat and
are lost with the session. Handoff is that home, for an effort that spans sessions. It holds:

- the state of each piece, including what is uncommitted or unpushed;
- the open questions, numbered once and never renumbered, so "question 3" means the same
  thing in every session, with each answer and its date written beside its question;
- the questions that are settled or handed to another plan, marked as such and naming the
  plan, so a later session does not raise them again;
- what is not verified;
- the order of the remaining work, and who each item waits on.

The test of a Handoff section is that a fresh session can start from "continue plan NNN" and
nothing else. A pick-up prompt that has to restate the state is a sign the section is missing
something.

## Length

Keep a plan under ~500 lines. Past that it gets hard to review and the
Log/Retrospective have nowhere left to grow — a plan that long is usually doing
too much at once. When a plan would cross ~500 lines (or already has), **propose
a split** rather than letting it sprawl. Splitting is a *proposal*: surface it
and confirm — never silently restructure an existing plan.

The guidance applies to **each file on its own**: the umbrella, and every subplan. What
grows in an umbrella after a split is its Log, so whole-effort entries stay short and point
to the subplan's Log for the detail.

**A plan is not split until it needs it.** Most plans are one file and stay that way. Split
when a plan would cross the length guidance, or when the user asks, and not before. A short
plan with a few ordered steps keeps them as a list.

When a split is due, it takes one of two forms:

- **Follow-ups** — carve the forward-looking remainder into separate, sequential
  plans (`NNN`, `NNN+1`, ...) that cross-link. Best when the pieces are
  independent or land at different times.
- **Steps (umbrella + nested subplans)** — keep the parent as an *umbrella* and move each
  step into a file under its own `subplans/` directory. Best when the steps are one effort
  done in order. See *Nested subplans* below.

## Nested subplans

**Subplans are nested**, whatever words the request uses: the parent stays as the *umbrella*
(goal, decisions, order, risks, out of scope, and the generated subplan table) and each step
is a file under the plan's `subplans/` directory, `<letter>-<step>.md`. "Sidecar" stays the
word for any other file in a plan directory. `{cli} add <slug> --parent <NNN> --nested`
scaffolds one. `--parent` without `--nested` makes a **lettered sibling plan**
(`<NNN><letter>-<slug>/plan.md`, `id` = the parent integer, `sub` = the letter) with its own
branch, PR, and lifecycle: made only when the request describes that shape, and folded back
by hand when made by mistake.

- **The subplan's frontmatter is the status of record** (`status`, `branch`, with `pr`,
  `needs`, and `moved_to` optional), and the umbrella's table is generated from it:
  `{cli} subplans <NNN> --set <letter>=<status>` changes one and regenerates the other in
  the same step, and `{cli} subplans <NNN>` checks the two. The table's Note column stays
  hand-written. A subplan has no `id`, so it is outside the index and `validate`
  (`validate --subplans` opts in).
- **Letters are fixed once assigned** and follow creation order; **an empty `branch` means
  the umbrella's branch**; **a subplan closes when its own work is finished**, not when the
  effort is.
- **An umbrella does not close over an unfinished subplan.** `{cli} subplans <NNN>
  --require-closed` and `{cli} retire <NNN>` refuse while one is `draft`, `active`,
  `implemented`, or `blocked`. A step carried to a follow-up plan closes as `retired` with
  `moved_to` (`{cli} retire <NNN><letter> --into <NNN>`); one partly done closes as `done`
  with what moved named in the Note column.

The `add` skill holds the authoring guidance: what the umbrella keeps and what goes to an
investigation subplan, the execution order as a dependency chain, and how to split a plan
that already exists.

## No local or personal specifics

Plans are shareable, reusable artifacts — keep them free of machine- or
person-specific detail. Never bake in real people's names, personal emails,
account handles, or absolute/local filepaths (e.g. `/home/<user>/...`). Use mock,
generalizable stand-ins instead:

- Names: `{Author}`, `Jane Doe`, or "the first author" — not a real person.
- Emails: `you@example.com` — never a real personal address.
- Repos / orgs / handles: `owner/repo`, `your-org/your-repo`.
- Paths: repo-relative (`data/...`, `docs/plans/...`) — never `/home/<user>/...`.

When a concrete identifier would only illustrate a point, generalize it (e.g. "the
open issue's tracker row", "a mis-linked submission") rather than naming a specific
person, email, or data row. Applies to the title, body, examples, and any sidecar files.

Write what the user said as the decision, convention, or correction it set, with its
reason, in the plan's own voice. Chat is candid and a plan is shared; translate between them.

**Enforcement by repo visibility.** On a **public** repo this is a hard blocker —
never write or commit a plan containing real names, personal emails, or local/absolute
paths; fix it before proceeding. On a **private** repo, **warn and continue** — surface
the specifics and offer to generalize, but don't block the work.

`{cli} log` checks paths for you: it refuses a note that names an absolute or
home-directory path (`/tmp/probe.py`, `~/scratch`, `C:\...`), before anything is
written, so the append-only Log never needs a rewrite to remove one. Describe the file
instead, or copy one worth keeping into the plan's directory as a sidecar.
`--allow-local-paths` writes the note anyway, for a private repo where the path has to
stay or a match that is not a local path (a URL route such as `/api/v1`).

## Updating Plans

Never overwrite plan content. Use targeted edits (small replacements of specific sentences) or
append new sections. Do not replace the entire plan body in one edit — large overwrites lose
the original thinking and make diffs unreadable.

When updating a plan after implementation, **append** new sections (Log, Retrospective) — do
not delete or condense existing plan content. The original spec is the historical record of
what was planned; the Log records what actually happened. Both are valuable.

**Handoff is the one exception.** It is rewritten in place, because it describes the present
and the Log keeps the history. The generated Status column of a subplan table is rewritten by
`{cli} subplans`, never by hand.

## Commits

Commit changes in logical chunks during implementation, not one large commit at the end.

### Plan commits belong on the mainline

The `plan [add]` and `plan [activate]` commits land on the **mainline before the
feature branch or worktree exists**, so the plan is recorded there even if the
branch never merges. Creating the branch first and running add/activate inside it
puts both commits only on that branch — a plan the mainline has no trace of.

`{cli} add`, `{cli} finalize`, and `{cli} activate` enforce this: they refuse when
HEAD is off the mainline, which is `dev` (when that branch exists) plus the repo's
default branch. `{cli} base --all` prints the set, read from git's current refs (`dev`,
then `origin/HEAD`, then a local `main`/`master`; the guard goes inert when none
resolve). `git fetch` does not refresh `origin/HEAD`; `git remote set-head origin --auto`
re-derives it. `--allow-branch` is for a repo whose mainline is genuinely not detectable
by name, not a way past the check.

The guard covers activating a `draft`, `blocked`, or `inactive` plan. Returning one from
`implemented` is not guarded, and `{cli} set-pr`, `{cli} implemented`, `{cli} log`,
`{cli} block`, `{cli} conclude`, and `{cli} retire` commit where they are run: the work is on its
feature branch, and a plan is retired wherever the decision is made. `conclude` checks instead that
HEAD is on the plan's recorded branch, since the date it records is that branch's.

### Plan commit subjects name the slug

`plan [<verb>]: {NNN} - <slug>` — the slug, not the title. That is what `{cli} add`,
`{cli} finalize`, `{cli} activate`, `{cli} set-pr`, `{cli} implemented`, `{cli} log`,
`{cli} block`, `{cli} conclude` (`plan [close]`), and `{cli} retire` write. A slug is fixed by the
directory name; a title can be reworded, so a title-derived subject drifts from the plan it names.
(`log` is the exception: `--summary` replaces the slug with a brief summary of the entry.)

## No Separate Summaries

Do not create a summaries directory. Session summaries belong in the plan's Log or
Retrospective section.

## Skills

Drive the lifecycle through the `/planners` skill (which replaces the retired `/plan-*`
skills):

- `/planners add` — scaffold a new plan
- `/planners implement` — run `{cli} start <NNN>` on the mainline (activate, branch from
  that commit, worktree, setup, draft PR; a re-run resumes, and each push stays the
  session's own command), then start coding
- `/planners update` — activate, log, close, or retire a plan
- `/planners close` — close end-to-end: log, retrospective, merge the PR, then `{cli} finish
  <NNN>` from the main checkout to clean up the worktree, branches, index, and hooks.
  "no PR" merges locally instead (`pr: null`) and asks first when a PR already exists;
  "minimal review" swaps the review loop for checks plus a diff skim
- `/planners pipeline` — drive a plan from implement to close in one run (pauses at the review gate)
- `/planners review` — check plans against the repo: a verdict and a dated Log
  entry per plan, retirements proposed (`planners review` itself only reads)
- `/planners index` — regenerate `.planners/README.md`
- `/planners backfill` — backfill missing frontmatter from git history and PRs

**Close-out steps are the session's to run.** Once the review gate has passed, the merge
and `{cli} finish` need no decision. A step goes to the user only after a call to it was
refused, with the refusal quoted; the `close` skill says how to tell a refusal from a
worktree that merely looks like an isolation block.

**Print a subcommand's instructions before describing it**, not only before running it:
`{cli} skill <subcommand>`. A lifecycle step described from memory is described wrongly, and
the instructions change with the installed version.

## Automation levels

The lifecycle commands shell out to git and `gh`; whether each runs unprompted
depends on the ambient Claude Code permission config. `{cli} permissions` prints the
allow rules for a level (`--help` has the options): `assist` (default) grants the local,
reversible spine plus the self-authored PR writes, `confirm` adds `git push`, and `full`
adds the irreversible `gh pr merge`.
