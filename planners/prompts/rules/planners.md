# Plan Files

Plan-file lifecycle is owned by the **`planners`** package (installed; the
`/planners` skill). Create, activate, log, close, index, and backfill plans through
`/planners` — not by hand. The package is the **source of truth**: run `{cli} schema
PlanMetadata` for the canonical field list and `{cli} validate` to check conformance
(a pre-commit hook gates it). This file is the always-on summary, itself generated by
`{cli} install` — do not hand-edit it; edit the convention in the package and reinstall.

## Storage layout

Plans live under **`.planners/`** at the repo root (git-tracked despite the leading dot):

    .planners/
      README.md                     # generated "# Plans" index table — do not hand-edit
      plans/<NNN>-<slug>/plan.md    # one DIRECTORY per plan (sidecar files allowed)

Identity (`id`/`slug`) validates against the **directory name**. Regenerate the index with
`{cli} index .` after changes; never hand-edit `.planners/README.md`. Human-authored docs
live in `docs/` — a curated `docs/README.md` landing page, never a generated plan table.

> **Migration in progress.** Some repos are still on the legacy `docs/plans/{NNN}-{slug}.md`
> + `TODO.md` layout. Keep using that layout in a repo until it is migrated to `.planners/`;
> new plans and migrated repos use `.planners/`.

## Naming

`<NNN>-<slug>` directory with an auto-incrementing prefix. Next number =
max(existing prefixes) + 1, and **the first plan in a fresh repo is `000`** —
numbering starts at zero, not one. Never reuse a number. `{cli} add <slug>`
scaffolds the directory, `plan.md`, and conformant frontmatter; check existing
plans first for the number.

For **batch creation**, do not run parallel `{cli} add`s — they can race on the
number. Instead, each creator runs `{cli} add <slug> --defer` to stage an
unnumbered plan under `.planners/staging/` (no commit, no shared state), then a
single `{cli} finalize` orders them by `created`, assigns sequential numbers,
materializes them under `plans/`, commits the batch, and self-checks — the sole
writer, so there is no race.

## Frontmatter

Every `plan.md` starts with YAML frontmatter (field order:
`id, slug, status, branch, created, concluded, pr` — keep all seven keys present):

    ---
    id: <int, = the NNN directory prefix>
    slug: <kebab-slug, = the directory slug>
    status: draft
    branch:
    created: YYYY-MM-DDTHH:MM:SS-TZ:TZ
    concluded:
    pr:
    ---

> **Field name.** The terminal-timestamp field is **`concluded`** — renamed from `completed`,
> shipped in planners 004 (>= 0.2.0) as a hard cutover with **no read-alias**. A legacy plan
> still keyed `completed:` fails `validate` (its `concluded` parses empty) until the key is
> renamed; rename the first frontmatter occurrence per file when migrating.

`status` is one of `draft`, `active`, `done`, `inactive`, `retired` (the shipped enum; the
neutral terminal status is `retired`, with no failure connotation). Update it as work
progresses: `draft` -> `active` -> `done` (or `retired`).
Use `inactive` for a plan that is parked or set aside without being implemented — considered
and deliberately shelved (e.g., it resolved to a one-line caveat, or describes a feature since
removed upstream) — but not formally closed and **may be revisited**. An `inactive` plan keeps
`concluded`, `branch`, and `pr` empty (it was never concluded); because `concluded` is empty it
sorts after done plans in the generated index.
Use `retired` for a plan that is **terminally closed because it was superseded or is no longer
needed** — e.g. its deliverable was absorbed into another plan or shipped by a different
mechanism. Unlike `inactive` it will not resume; it carries no failure connotation (the goal
was met another way, or made moot) — the neutral "this is dead" state. Fill `concluded` with
the date it was retired, and treat absent `branch`/`pr` as explicit `null` (it's
closed), the same as `done`.
Use real timestamps — run `date -Iseconds`. Never fabricate or guess timestamps.
For `concluded`, use the timestamp from the relevant git commit (`git log --format="%aI"`),
not the current time or an estimate. Fill it for `done` and `retired`; leave it empty for
`inactive` plans (they were parked, not concluded).
Fill `pr` with the full PR URL (e.g., `https://github.com/owner/repo/pull/1`), not just the
number.

**Empty vs `null`.** An empty value (`pr:`) means "pending / not yet determined" — use it for
a field that may still be filled (an open plan's `concluded`/`pr`, or a branch not yet
assigned). Explicit `null` means "closed and confirmed absent" — use it only once a plan is
**closed** (done/retired, not `inactive`) and a field is genuinely N/A, e.g. it merged with no
dedicated PR (`pr: null`) or involved no branch (`branch: null`). An `inactive` plan uses empty
(pending) fields, not `null`, since it may resume. Both parse to YAML null, but the distinction
is a readable signal. Never write the string `none`/`None` — YAML reads those as strings.

## Title

Every plan needs a `# Title` heading after the frontmatter. Do not include the plan number or
"Plan:" prefix — the number is in the directory name. The title must describe the work, not be
generic (not "Plan", "Update", "Fix"). Write it in **sentence case**, not Title Case —
capitalize only the first word and any proper nouns or code identifiers (e.g.
"Migrate pandas to polars", "Add compressed test fixtures for CI", "Honor core.hooksPath when
detecting the hook"), never "Migrate Pandas To Polars". A good title summarizes the goal or
change.

## Body Sections

- **Plan** — implementation spec (required)
- **Log** — chronological notes, commits, decisions (optional, append during work)
- **Retrospective** — post-completion insights (optional, add when done)

## Length

Keep a plan under ~500 lines. Past that it gets hard to review and the
Log/Retrospective have nowhere left to grow — a plan that long is usually doing
too much at once. When a plan would cross ~500 lines (or already has), **propose
a split** rather than letting it sprawl. Splitting is a *proposal*: surface it
and confirm — never silently restructure an existing plan.

- **Follow-ups** — carve the forward-looking remainder into separate, sequential
  plans (`NNN`, `NNN+1`, ...) that cross-link. Best when the pieces are
  independent or land at different times.
- **Steps (umbrella + subplans)** — keep the parent as an *umbrella* whose
  `## Plan` is just a subplan table (scope + status per step) plus the execution
  order, and move each step into its own `<NNN><letter>-<slug>` subplan
  (`015a`, `015b`, ...). The parent keeps its original metadata and stays `active`
  until the chain completes. Best when the steps are one effort done in order.
  The canonical shape is an `015` umbrella + `015a`-`015e` subplans. (Under
  `.planners/`, subplans use the `sub` field added in **planners
  0.2.7**: directory `<NNN><letter>-<slug>/plan.md`, `id` = the parent integer,
  `sub` = the letter (`015a` -> `id: 15, sub: a`); ordinary/umbrella plans omit
  `sub:`. Requires planners >= 0.2.7 — releases <= 0.2.6 silently ignore
  letter-suffix directories, so upgrade before migrating an umbrella repo.)

## No local or personal specifics

Plans are shareable, reusable artifacts — keep them free of machine- or
person-specific detail. Never bake in real people's names, personal emails,
account handles, or absolute/local filepaths (e.g. `/home/<user>/...`). Use mock,
generalizable stand-ins instead:

- Names: `{Author}`, `Jane Doe`, or "the first author" — not a real person.
- Emails: `you@example.com` — never a real personal address.
- Repos / orgs / handles: `owner/repo`, `your-org/your-repo`.
- Paths: repo-relative (`data/...`, `docs/plans/...`) — never `/home/<user>/...`.

When a concrete identifier would only illustrate a point, generalize it (e.g. "the
open issue's tracker row", "a mis-linked submission") rather than naming a specific
person, email, or data row. Applies to the title, body, examples, and any sidecar files.

**Enforcement by repo visibility.** On a **public** repo this is a hard blocker —
never write or commit a plan containing real names, personal emails, or local/absolute
paths; fix it before proceeding. On a **private** repo, **warn and continue** — surface
the specifics and offer to generalize, but don't block the work.

## Updating Plans

Never overwrite plan content. Use targeted edits (small replacements of specific sentences) or
append new sections. Do not replace the entire plan body in one edit — large overwrites lose
the original thinking and make diffs unreadable.

When updating a plan after implementation, **append** new sections (Log, Retrospective) — do
not delete or condense existing plan content. The original spec is the historical record of
what was planned; the Log records what actually happened. Both are valuable.

## Commits

Commit changes in logical chunks during implementation, not one large commit at the end.

### Plan commits belong on the mainline

The `plan [add]` and `plan [activate]` commits land on the **mainline before the
feature branch or worktree exists**, so the plan is recorded there even if the
branch never merges. Creating the branch first and running add/activate inside it
puts both commits only on that branch — a plan the mainline has no trace of.

`{cli} add` and `{cli} finalize` enforce this: they refuse when HEAD is off the
mainline. The accepted set is `dev` (when that branch exists) plus the repo's
default branch, so a plan added on either is fine; `{cli} base --all` prints it.
`--allow-branch` overrides the refusal, and is for a repo whose mainline is
genuinely not detectable by name — not a way past the check.

Detection is a heuristic over git's current refs, not a record of where plans
were committed. It reads `dev`, then `refs/remotes/origin/HEAD`, then a local
`main`/`master`, and goes **inert** (never blocks) when none resolve or the repo
has no commits yet. `git fetch` does not refresh `origin/HEAD`, so it can be
unset or stale; `git remote set-head origin --auto` re-derives it.

The activation commit is hand-written `git commit`, so no CLI guard covers it —
check `git branch --show-current` against `{cli} base --all` before making it.

## No Separate Summaries

Do not create a summaries directory. Session summaries belong in the plan's Log or
Retrospective section.

## Skills

Drive the lifecycle through the `/planners` skill (which replaces the retired `/plan-*`
skills):

- `/planners add` — scaffold a new plan
- `/planners implement` — check git status, create branch, activate, start coding
- `/planners update` — activate, log, close, or retire a plan
- `/planners close` — close end-to-end: log, retrospective, merge PR, clean up branch
- `/planners pipeline` — drive a plan from implement to close in one run (pauses at the review gate)
- `/planners index` — regenerate `.planners/README.md`
- `/planners backfill` — backfill missing frontmatter from git history and PRs

## Automation levels

The lifecycle commands shell out to git and `gh`; whether each runs unprompted
depends on the ambient Claude Code permission config. `{cli} permissions
[--level none|assist|confirm|full]` prints (or, with `--apply`, additively
merges) a matching allow-rule profile so you can pick how hands-off the run is:
`assist` (default) grants the local, reversible spine plus the self-authored PR
writes; `confirm` adds `git push`; `full` adds the irreversible `gh pr merge`. It
writes the repo's `.claude/settings.local.json` by default (`--global` for the
user-wide file) and never downgrades an existing `deny`/`ask` rule.
